# Конвейер агентной разработки v8vscedit

Опорный документ **оркестратора** (основного чата Claude Code) и всех субагентов: роли, порядок,
треки и протокол. Определения агентов — в `.claude/agents/*.md`. Обязательный стандарт
качества — [vscode-extension-best-practices.md](./vscode-extension-best-practices.md); контракт
архитектуры — корневой [`CLAUDE.md`](../CLAUDE.md); рецепты изменений по сценариям —
[change-recipes.md](./change-recipes.md).

## Цель

Управляемый TDD-конвейер вместо «одного чата на всё». Проектирование, реализация и ревью разведены по
ролям. Ревью и регресс с покрытием обязательны на каждой задаче. Мелкие задачи не гоняются по полному
треку, документация поддерживается в актуальном состоянии. Механическую работу (прогон тестов,
покрытие, lint, sanity-проверки) выполняет скрипт, а не LLM-агент.

## Роли

| Роль | Где | Модель | Инструменты | Суть |
|---|---|---|---|---|
| **Оркестратор** | основной чат | — | все | Триаж, выбор трека, передача между стадиями, запуск qa-gate, синтез результата |
| **Архитектор** | `.claude/agents/architect.md` | opus | read-only | Изучает ТЗ и код, готовит план реализации с сигнатурами и планом тестов. Код не пишет |
| **Реализатор** | `.claude/agents/implementer.md` | opus | все правки | TDD в одном контексте: контракт → красные тесты → реализация до «зелёного» → compile + lint |
| **QA-гейт** | `.claude/scripts/qa-gate.sh` | — (скрипт) | — | lint + sanity-проверки + один полный прогон `coverage:changed` (он же регресс). Краткая сводка GREEN/RED |
| **QA / разбор** | `.claude/agents/qa-e2e.md` | sonnet | Bash + правка тестов | Только при RED гейта: разбирает полный лог, классифицирует падения, чинит тесты/E2E или указывает, кому вернуть |
| **Ревьюер** | `.claude/agents/reviewer.md` | opus | read-only + Bash | ТЗ, конвенции, SOLID, best-practices, качество и независимость тестов. Вердикт/возврат |
| **Документатор** | `.claude/agents/documenter.md` | sonnet | доки | В конце дополняет `docs/` и рецепты для будущих планов |

### Почему так устроено (замер расхода токенов)

Раньше в конвейере было шесть LLM-стадий: test-writer и developer были отдельными агентами, QA тоже
выполнял агент. По транскриптам 118 запусков субагентов:

- автор тестов тратил около 72% всех токенов конвейера: около 110 вызовов инструментов за запуск,
  контекст до 800k. Тесты писались под ещё не существующий API, поэтому «красный» сначала получался на
  компиляции, а на передаче тестов разработчику контекст терялся;
- QA-агент тратил около 7% токенов, зато вдвое удлинял стадию по времени: `npm test` и затем
  `coverage:changed`, который сам запускает полный `npm test` вместе с pretest;
- 71 КБ `CLAUDE.md` загружались в каждый ход каждого агента.

Отсюда три решения: test-writer и developer объединены в `implementer`, у которого сначала контракт,
потом тесты, потом код. Механический QA заменён скриптом с одним прогоном. Рецепты сценариев и
раскладка каталогов вынесены из `CLAUDE.md` в `docs/`.

## Поток

```
Оркестратор — триаж задачи
   │
   ├── FAST-трек (мелкая, нерисковая):
   │      оркестратор реализует сам (тест + код)
   │        → qa-gate  ──RED──→ qa-e2e (разбор) → возврат/починка → qa-gate
   │        → reviewer
   │        → [documenter — если изменился публичный контракт/поведение/архитектура]
   │
   └── FULL-трек (крупная/рисковая):
          architect (план + сигнатуры + план тестов)
            → implementer (контракт → красный → зелёный; только связанные тесты + compile + lint)
            → qa-gate  ──RED──→ qa-e2e (разбор) → возврат/починка → qa-gate
            → reviewer
            → documenter
```

**Инвариант: `reviewer` и QA-гейт выполняются ВСЕГДА**, на любом треке. Меняется только объём
предшествующих стадий. Агент `qa-e2e` запускается только по RED гейта или по явной просьбе.

**Нерантайм-изменения** (`.claude/**`, `.gitignore`, `docs/` без кода, конфигурация инструментария)
гейт распознаёт сам: выполняет lint и sanity-проверки, а `npm test`/`coverage:changed` помечает `N/A`.
Как только задача касается `src/**`, `src-ui/**`, `scripts/**`, `package.json`, конфигов сборки или
тестов, гейт гоняет полный прогон. `reviewer` выполняется в любом случае.

## Триаж: FAST vs FULL

Оркестратор выбирает **FULL-трек**, если задача попадает хотя бы в один пункт:

- правит центральные контракты: `META_TYPES`, `MetaPathResolver`, `PropertySchema`,
  `TypedFieldPropertyRules`, ruleset формата (`infra/xml/format/`);
- добавляет тип метаданных / слот модуля (`ModuleSlot`) / дочерний тег (`ChildTag`) / схему свойств;
- добавляет или меняет MCP-инструмент (`V8McpServer` + `EXTENSION_MCP_TOOLS`) либо канон путей;
- добавляет команду, view/webview-провайдер, декорацию узла, watcher;
- меняет публичный контракт webview ↔ расширение (`src-ui/shared/protocol/`);
- миграции парсинга XML, работа с BOM/EOL, генерация XML;
- затрагивает > 2–3 файлов или пересекает границы слоёв (domain/infra/ui/lsp/cli).

Иначе — **FAST-трек**: локальная правка одного файла, узкий баг-фикс, правка комментария/дока,
переименование внутри модуля. При сомнении — FULL: цена лишнего архитектора ниже цены пропущенного риска.

## TDD-петля (FULL-трек)

1. **Архитектор** возвращает план: затрагиваемые слои/файлы по рецепту из
   [change-recipes.md](./change-recipes.md), привязку к `META_TYPES`/`MetaPathResolver`, риски,
   критерии приёмки, **сигнатуры новых/меняемых публичных функций и типов** и перечень тестов:
   фикстуры, ветки, параметризация. Сигнатуры нужны, чтобы тесты сразу компилировались.
2. **Реализатор** ведёт всю петлю в одном контексте:
   - заводит контракт по сигнатурам плана (заглушки с `throw`);
   - пишет **все** тесты задачи за один проход на реальных фикстурах (`example/2.20/src/cf`,
     `example/2.21/src/cf`, `example/2.21/src/cfe/EVOLC`) или реальных временных файлах, с заранее
     перечисленными ветками для 100% покрытия изменённого и параметризацией по конечным множествам;
   - убеждается, что красный — по правильной причине, то есть на ассертах;
   - реализует минимальным изменением до «зелёного»; гоняет только связанные тесты
     (`test:compile` → `MOCHA_GREP=… test:fast`), затем `compile` + `lint`.
3. **QA-гейт** запускает оркестратор: `bash .claude/scripts/qa-gate.sh` (база по умолчанию `main`,
   иначе — первый аргумент). Внутри:
   - lint и sanity-проверки из `CLAUDE.md`;
   - `COVERAGE_BASE_REF=<база> npm run coverage:changed` — полный `npm test` под c8, то есть регресс и
     гейт покрытия изменённого (100%) за один прогон;
   - если файлов для patch-покрытия нет (правки только в тестах, фикстурах, сборке или `Container.ts`), вместо
     него идёт обычный `npm test`.

   Скрипт печатает сводку: passing/failing/pending, упавшие тесты, непокрытые строки. Полный лог
   пишется в `out/qa-gate.log`. Базовое состояние набора — 0 failing, поэтому любое падение считается
   регрессией.
4. **При RED** оркестратор решает по сводке. Очевидную причину (непокрытая ветка, падение своего
   нового теста) он сразу возвращает `implementer`. Неочевидную отдаёт агенту `qa-e2e` на разбор по
   `out/qa-gate.log`, повторный прогон тестов при этом не нужен. После починки гейт запускается снова.
   Флейк — дефект теста, а не повод для повторов.
5. **Ревьюер** получает отчёт реализатора и сводку гейта и выносит вердикт (см. ниже). Compile, lint и
   sanity-проверки он заново не гоняет: они уже в сводке гейта.
6. **Документатор** актуализирует документацию и отдельно перечисляет протухшие комментарии в
   `src/**`, найденные по ходу задачи. Найти он их может, но исправить нет: `src/**` ему закрыт хуком.
   Если список не пуст, оркестратор до завершения задачи закрывает его микро-возвратом: правит
   комментарии сам или передаёт `implementer`, если правок много. Пустой список означает, что стадия
   завершена.

На FAST-треке шаги 1–2 выполняет оркестратор (тест + код), далее шаги 3–6 без изменений.

**Песочница Bash и тестовые команды.** `npm test`/`npm run test:fast` и `qa-gate.sh` запускают
Electron-хост (`@vscode/test-electron`), который под стандартной песочницей Bash убивается сигналом.
Эти команды числятся в `sandbox.excludedCommands` проектного `.claude/settings.json`. Сигнал — это
ограничение окружения, а не повод подменять живой прогон статической проверкой (`tsc --noEmit`).
Без дисплея гейт сам оборачивает прогон в `xvfb-run -a`.

**Фикстуры `example/`.** Каталог `example/` версионируется: это настоящая выгрузка платформы 1С
(конфигурация «Торговый учёт» на поддержке поставщика, форматы 2.20 и 2.21, расширение EVOLC),
собранная скриптом `example/tools/build-supported-cf.mjs` (порядок сборки и формат
`ParentConfigurations.bin` — в шапке скрипта, разбор формата — см.
[architecture.md](./architecture.md#режим-поддержки-поставщика-parentconfigurationsbin)). Если тесту
не хватает объекта в фикстуре, конфигурацию дополняют и пересобирают выгрузку скриптом, XML руками не
правят. Ожидаемые значения берутся из фикстуры по имени объекта, а не по uuid (uuid задаёт
Конфигуратор). Отдельная фикстура `example/support/changes-forbidden/ParentConfigurations.bin`
(правила `example/tools/support-rules-forbidden.json`) — конфигурация с флагом заголовка «изменения
запрещены»; её используют тесты `SupportMode.Locked` для всей конфигурации целиком.

## Протокол возврата (reviewer)

Ревьюер завершает одним из:

- **APPROVE** — соответствует ТЗ, конвенциям, SOLID, best-practices; гейт GREEN.
- **RETURN → implementer** — дефекты реализации, стиля, SOLID, тестов или покрытия. Список конкретных
  замечаний (файл:строка, что не так, чем чревато).
- **RETURN → architect** — расхождение с ТЗ пользователя или архитектурный дефект: утечка знаний из
  `META_TYPES`, нарушение границ слоёв, дублирующий реестр.

После доработки стадии повторяются начиная с точки возврата, затем снова QA-гейт и `reviewer`.

## Эффективность (обязанности оркестратора)

- **Бриф — один на задачу.** Реализатор получает план целиком: все тесты, все ветки, параметризацию.
  Отдельные вызовы «дописать тест на X» — лишние циклы; исключение — реальный возврат от
  reviewer/гейта.
- **Не пересказывай CLAUDE.md в брифе** — он уже в контексте каждого агента. Передавай план, файлы и
  критерии приёмки.
- **Гейт покрытия — только `coverage:changed`** (через qa-gate), глобальный `coverage` красный из-за
  легаси и основанием для RED не является.
- **Не зови `qa-e2e` на зелёный гейт** и не проси его «ещё раз прогнать для надёжности».

## Обязательства агентов (общие)

`CLAUDE.md` загружен в контекст каждого агента автоматически, перечитывать его файлом не нужно. По
задаче агенты читают:

- [change-recipes.md](./change-recipes.md) — рецепт сценария (`architect`, `reviewer`; `implementer` —
  раздел, на который ссылается план);
- [vscode-extension-best-practices.md](./vscode-extension-best-practices.md) — обязателен для
  `architect` и `reviewer`;
- профильные `docs/` (`architecture.md`, `metadata-navigator.md`, `mcp-paths.md`,
  `xml-format-rulesets.md` и др.) — только разделы по затрагиваемой области.

Единый источник правды в промптах агентов не дублируется: агенты **ссылаются** на эти документы.

## Границы

- Оркестратор — основной чат, а не отдельный файл-агент; его поведение задаётся `CLAUDE.md`.
- Субагенты запускаются оркестратором; друг друга они напрямую не запускают — последовательность и
  передачу результатов контролирует оркестратор.
- Разделение прав по ролям: `architect`/`reviewer` — read-only, `documenter` — только документация
  (хук `.claude/hooks/restrict-write-paths.mjs`), `qa-e2e` — только тесты и E2E-фикстуры по промпту.

## Git-процесс

- Коммиты — на русском, **без упоминаний Claude / `Co-Authored-By`** (см. `CLAUDE.md`).
- **Ветки создаёт только пользователь** — агенты и оркестратор не создают ветки автоматически.
- Перед завершением задачи QA-гейт должен быть GREEN: lint, sanity, `npm test` и `coverage:changed`
  (100% patch coverage по изменённым файлам).
