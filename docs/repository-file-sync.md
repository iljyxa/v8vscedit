# Синхронизация файлов проекта с хранилищем конфигурации

Issue #1 форка. Команды хранилища `v8vscedit.repository.lock` / `update` / `unlock` / `commit` меняют не только
состояние объектов на сервере и в базе, но и файлы XML-выгрузки проекта. Полный план и решения —
[plans/repository-file-sync-plan.md](./plans/repository-file-sync-plan.md) (разделы 1–10), факты поведения
платформы, на которых держится реализация, — там же, §10.12.

## Модель: файлы проекта — форк хранилища

- **Захват** — получить в проект актуальную версию хранилища (захват всегда с `-revised`).
- **Получение** — то же без захвата.
- **Отмена захвата** — отказаться от своих правок и вернуть файлы к версии хранилища.
- **Помещение** — отдать правки в хранилище; без `keepLocked` это одновременно отмена захвата.

Выгрузка из базы небыстрая (каждый запуск Конфигуратора — секунды–десятки секунд на реальной базе), поэтому
выгружается только затронутое и минимальным числом запусков.

## Единица хранилища

Платформа хранит как отдельные объекты не только объекты верхнего уровня, но и подчинённые объекты со
своим XML: у них собственный захват, собственная запись в `ConfigDumpInfo.xml` и собственное имя в
`-listFile`. Частичная выгрузка владельца их **не** включает (проверено на 8.5.1). Команды, модули объекта,
справка, `Rights.xml`, `Predefined.xml` выгружаются вместе с владельцем.

Раскладка подчинённых — `REPOSITORY_SUBORDINATE_LAYOUT` (`infra/repository/RepositoryObjectNames.ts`):

| Тег ChildObjects | Каталог | Имя в `-listFile` / `Objects.xml` |
|---|---|---|
| `Form` | `Forms` | `Справочник.X.Форма.Y` |
| `Template` | `Templates` | `Справочник.X.Макет.Y` |
| `Recalculation` | `Recalculations` | `РегистрРасчета.X.Перерасчет.Y` |
| `Table` | `Tables` | `ВнешнийИсточникДанных.X.Таблица.Y` |
| `Cube` | `Cubes` | `ВнешнийИсточникДанных.X.Куб.Y` |
| `DimensionTable` | `DimensionTables` | `…Куб.Y.ТаблицаИзмерения.Z` |
| `Subsystem` | `Subsystems` | `Подсистема.A.Подсистема.B` |

Корень — `Конфигурация.<Name>` (и для расширения с `-Extension`); в `state.json` он представлен сентинелами
`__configuration_root__` / `__extension_root__`. Имена в трёх алфавитах (fullName хранилища, ссылка
ChildObjects/ConfigDumpInfo, путь выгрузки) переводятся только в `RepositoryObjectNames` и
`RepositoryObjectScope`. Несуществующее в базе имя в `-listFile` роняет **всю** выгрузку — поэтому имена
подчинённых берутся только из источника, соответствующего базе.

### Области файлов

`ObjectScope` (`RepositoryObjectScope.ts`) — набор файлов единицы:

- `unit` — XML единицы и её каталог **без** каталогов подчинённых единиц (Forms, Templates, …). Слияние,
  снимки и сравнение работают только с этой глубиной.
- `tree` — весь каталог. Только для единиц, удалённых из хранилища, и старых («глубоких») снимков.
- `root` — `Configuration.xml` + корневой `Ext/**`; `all` — вся конфигурация (запасная полная выгрузка).

Файлы подчинённых, не участвующих в операции, не входят в область — они не перезаписываются и не удаляются.

## Потоки и блокировка Конфигуратора

Потоки — `ui/commands/repository/RepositoryLockSync.ts` (захват/получение) и `RepositoryUnlockSync.ts`
(отмена/помещение), эталоны отмены — `RepositoryUnlockEtalons.ts`. Все внешние точки (CLI, выгрузка,
диалоги) внедряются через `RepositoryFileSyncDeps` (`RepositoryFileSyncShared.ts`).

1. `ensureRepositoryGuardFree` — занятость `ConfigurationOperationGuard` проверяется **до** первого
   QuickPick; при занятости — лог `[repository][file-sync][busy] … "<heldBy>"` и `notifyBusy` без `await`.
2. Хеш-кэш (и для рекурсивного корня — хеши файлов проекта) читается до аренды.
3. **Одна аренда** `runExclusive`: CLI хранилища → `applyLock`/`applyUnlock` → выгрузка во временный каталог.
   Внутри аренды нет диалогов и `await vscode.window.show*` (запрет №18).
4. После аренды: слияние, единственный модальный диалог, запись файлов, снимки, post-mutation, сообщения.

Выгрузка никогда не пишется сразу в проект: временный каталог → план слияния → применение.
`ConfigDumpInfo.xml` частичной выгрузкой не создаётся; проектный заменяется только после успешного
root-incremental.

### Раунды выгрузки (`RepositoryDumpRounds.ts`)

Оптимистичная схема: в обычном случае **один** запуск Конфигуратора.

1. Раунд 0 — якоря операции плюс замыкание раскрытия по **проектному** XML; не-якорные имена берутся, только
   если XML единицы есть в хеш-кэше (единица известна базе).
2. Раунд 0 упал (в списке имя, которого уже нет в базе) → повтор только якорями.
3. Раунды 1…N — раскрытие новых найденных единиц по их XML **из выгрузки** (версия хранилища); пусто — стоп.
   Предел `MAX_DUMP_ROUNDS = 5` по всем запускам; недовыгруженные единицы → `missing`: в слияние не входят,
   их файлы не трогаются, после аренды — предупреждение «выполните повторно».

Стратегии раскрытия: `subordinates` (рекурсивная операция над объектом; куб — ещё уровень таблиц измерения),
`subsystem` (рекурсивная подсистема: вложенные подсистемы, участники `<Content>` и их подчинённые —
`SUBSYSTEM_MEMBERS_INCLUDE_SUBORDINATES = true`, т.к. рекурсивный захват подсистемы захватывает формы
участников), `new-subordinates` (нерекурсивная операция: только подчинённые, которых нет в проекте —
платформа довозит новые формы и при нерекурсивном захвате/получении, но не захватывает их), `towards`
(отмена без снимка), `none` (root-incremental: точные имена, один раунд).

### Рекурсивный корень (root-incremental)

`-configDumpInfoOnly` во временный каталог → `diffConfigDumpInfo(проектный, новый, extractDumpInfoUnit)` по
единицам (`Catalog.X.Form.Y.Form` → `Catalog.X.Form.Y`) → частичная выгрузка только изменённых и добавленных
единиц. `configVersion` меняется только у полученных единиц, поэтому повтор без изменений не запускает
вторую выгрузку. Полная выгрузка во временный каталог — запасной путь: нет проектного `ConfigDumpInfo.xml`,
он не разобрался, сбой `-configDumpInfoOnly`, пустой новый файл при непустом проектном, изменено больше
`ROOT_INCREMENTAL_MAX_OWNERS = 400` единиц или больше `ROOT_INCREMENTAL_MAX_SHARE = 50%`.

## Трёхстороннее слияние

`RepositoryMergePlanner.ts` (чистый план) и `RepositoryMergeApplier.ts` (применение). Для каждого файла
области: **R** — версия хранилища (выгрузка), **L** — локальный файл, **B** — база (хеш-кэш, для файлов вне
кэша — снимок).

| Состояние | Действие |
|---|---|
| L == R | ничего |
| L == B (или нет ни L, ни B) | записать молча |
| прочее при наличии R | конфликт-запись |
| нет R, L == B | удалить молча |
| нет R, L ≠ B | конфликт-удаление |
| файл открыт с несохранёнными правками | всегда конфликт |

При конфликтах — **один** модальный диалог на операцию: «Сравнить» / «Заменить из хранилища»; Esc = «оставить
локальное» (`keep-local`):

- **Заменить / Сравнить** — локальная версия сначала уходит в бэкап
  `.v8vscedit/repository/merge/<scopeKey>/<время>-<метка>/<rel>`, затем файл перезаписывается побайтово
  (BOM/EOL версии хранилища). «Сравнить» открывает до `MAX_DIFF_TABS = 10` диффов «бэкап ↔ файл проекта»
  (только текстовые файлы, остальные — в журнал).
- **Esc** — конфликтные файлы не трогаются; версия хранилища кладётся в `…/merge/…/repository/<rel>`, хеш в
  кэше = хеш хранилища (файлы помечаются изменёнными), немодальное сообщение с кнопкой «Сравнить».

Перед записью хеш локального файла перепроверяется (правка между планом и применением → бэкап). После
применения хеш-кэш = состояние базы. Новые объекты верхнего уровня добавляются в `ChildObjects`
`Configuration.xml` через `ConfigurationXmlEditor` (`ConfigurationChildObjectsSync.ts`).

Post-mutation: `suppressConfigurationReloadForFiles` → запись и патч хеш-кэша → `markChangedConfigurationByFiles`
для оставленных расхождений → структурные изменения ⇒ `reloadEntries()`, иначе
`treeProvider.refreshCacheForFiles` → `refreshActionsView()`. `changeDetector.detect()` не вызывается.

## Снимки и отмена захвата

`RepositoryLockSnapshotStore.ts`, раскладка
`.v8vscedit/repository/snapshots/<scopeKey>/<sha1(fullName)>/{manifest.json,files/<rel>}`.

- Снимок = ровно версия хранилища, по одному на захваченную единицу. Манифест v3:
  `{version: 3, files, hashes, depth: 'unit'|'tree', subordinates?}`; v1/v2 читаются как `depth: 'tree'`.
- Рекурсивный корень вместо снимков хранит хеш-манифест `root-manifest.json` (без копий файлов). Файлы,
  оставленные при keep-local, фиксируются в нём хешем хранилища; оставленные локальные файлы, которых в
  хранилище нет, в манифест не попадают — при отмене они считаются расхождением.
- Получение пересоздаёт снимки только захваченным единицам; помещение с `keepLocked` снимает снимок из
  проекта; без `keepLocked` снимки удаляются.

Эталон при отмене (`RepositoryUnlockEtalons.ts`), единицы обходятся от предков к потомкам: покрыта предком с
`tree` → пропуск; свой снимок → эталон-снимок; у предка снимок v3 с `subordinates` без этой единицы (создана
локально) → эталон «пусто» без Конфигуратора; иначе — выгрузка в той же аренде (`towards`). Рекурсивный корень
сравнивает текущие хеши с манифестом (или хеш-кэшем) и выгружает только изменившиеся единицы; изменений нет —
Конфигуратор не запускается.

Расхождения с эталоном → модальный «Откатить к версии хранилища» / «Оставить изменения» (Esc = оставить).
Откат делает бэкап каждого перезаписываемого и удаляемого файла, удаляет лишние файлы области. При обоих
исходах хеш-кэш = эталон, оставленные файлы помечаются изменёнными.

## Состояние захватов (`state.json`)

`.v8vscedit/repository/state.json`, формат `version: 2` (`RepositoryLockState.ts`). Необязательные поля цели:
`rootRecursive`, `releasedUnderRoot`, `lockGroups` (якорь → состав рекурсивного захвата), `lockModes`
(`'recursive' | 'object'` — режим последнего захвата единицы). Некорректные значения при чтении отбрасываются.

`isLocked(target, unit)` = явно захвачена ИЛИ участник группы ИЛИ под рекурсивным корнем и не освобождена ИЛИ
(правило старых записей) захвачен предок без записи в `lockModes`. Нерекурсивная отмена якоря группы снимает
только якорь — на сервере подчинённые остаются захваченными.

## Readonly

`RepositoryService.isEditRestricted(filePath)` определяет единицу по пути (только строковые операции) и
требует её захвата: при нерекурсивном захвате справочника файлы форм и макетов остаются только для чтения
(на сервере они не захвачены — загрузка их в базу была бы отклонена), при рекурсивном — редактируемы.
`EditorReadonlyController` (`ui/readonly/`) подписан на `onDidChangeLocks` и по чистому плану
`planReadonlyTransitions` переключает readonly открытых вкладок (включая правую сторону диффа) без
переоткрытия: видимые — сразу, скрытые — при активации.

## Настройка

`v8vscedit.repository.syncFilesOnLockUnlock` (по умолчанию `true`) включает выгрузку, слияние, снимки и откат.
Захват с `-revised`, guard, состояние захватов и readonly работают всегда. MCP-инструмента нет: команды
`v8vscedit.repository.*` не входят в `ALLOWED_COMMANDS` моста `v8vscedit_execute_command` — все четыре операции
требуют интерактивных решений пользователя (рекурсия, конфликты, откат).

## Известные ограничения

- Повторный захват `-revised` уже захваченного объекта перетирает в **базе** непомещённые правки версией
  хранилища (поведение платформы); локальные файлы защищает слияние, а оставленные правки помечаются
  изменёнными и уйдут в базу следующим импортом.
- Старые записи `state.json` (без `lockModes`) трактуются как раньше: захват владельца делает редактируемыми и
  файлы подчинённых. Запись становится точной после следующего захвата/отмены.
- Хеши файлов корня при отмене рекурсивного захвата корня считаются до аренды синхронно по всей конфигурации;
  правки, сделанные во время самой операции, в сравнение не попадают.
- При событии захвата видимые вкладки корневых файлов (`Configuration.xml`, `Ext/*.bsl`) переактивируются даже
  при захвате другого объекта — кратковременное переключение фокуса.
- Пустые каталоги-контейнеры (`Forms/`) после удаления последней формы остаются.
- Удаление подчинённого объекта в хранилище при нерекурсивном получении платформой не проверено; такие файлы
  не трогаются, в журнал пишется предупреждение.
- `bind`/`create`/`unbind`/`report`/`dump`/`users`/`label` идут мимо guard'а (issue #40).
- Команды с узла формы/макета захватывают владельца (issue #45); значок захвата и свойства формы считаются по
  владельцу (issue #46); режим поддержки перерасчётов/таблиц/вложенных подсистем берётся от владельца (#47).
- Тесты вложенных подсистем временно на синтетике, «удалённая в хранилище форма» — правкой копии реального XML:
  ждут фикстуры F1/F4 (issue #48).

## Ручная проверка на Конфигураторе

Проверено в пакетном режиме (§10.12 плана): имена `-listFile`, состав частичной выгрузки, `-configDumpInfoOnly`,
`-revised`, `unlock` с `-force` и без, рекурсивный и нерекурсивный захват объекта и подсистемы, нерекурсивная
отмена после рекурсивного захвата, новая форма при нерекурсивном получении/захвате. Остаётся проверить в
интерактивном VS Code: readonly скрытой вкладки и правой стороны диффа, `files.readonlyInclude`, диалог
конфликта с реальным сценарием двух пользователей, режим агента конфигуратора, расширение (cfe) с формами.
