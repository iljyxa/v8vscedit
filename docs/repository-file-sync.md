# Синхронизация файлов проекта с хранилищем конфигурации

Issue #1 форка. Команды хранилища `v8vscedit.repository.lock` / `update` / `updateToVersion` / `unlock` / `commit`
меняют не только состояние объектов на сервере и в базе, но и файлы XML-выгрузки проекта. Полный план и решения —
[plans/repository-file-sync-plan.md](./plans/repository-file-sync-plan.md) (разделы 1–10), факты поведения
платформы, на которых держится реализация, — там же, §10.12.

## Модель: файлы проекта — форк хранилища

- **Захват** — получить в проект актуальную версию хранилища (захват всегда с `-revised`).
- **Получение** — то же без захвата.
- **Отмена захвата** — отказаться от своих правок и вернуть файлы к версии хранилища.
- **Помещение** — отдать правки в хранилище; без `keepLocked` это одновременно отмена захвата.

Выгрузка из базы небыстрая (каждый запуск Конфигуратора — секунды–десятки секунд на реальной базе), поэтому
выгружается только затронутое и минимальным числом запусков.

## Единица хранилища

Платформа хранит как отдельные объекты не только объекты верхнего уровня, но и подчинённые объекты со
своим XML: у них собственный захват, собственная запись в `ConfigDumpInfo.xml` и собственное имя в
`-listFile`. Частичная выгрузка владельца их **не** включает (проверено на 8.5.1). Команды, модули объекта,
справка, `Rights.xml`, `Predefined.xml` выгружаются вместе с владельцем.

Команды хранилища (захват/отмена/помещение/получение), запущенные с узла **формы или макета**, адресуют
**саму эту единицу** (`Владелец.Форма.Имя` / `Владелец.Макет.Имя`, `RepositoryService.resolveFullName` →
`buildSubordinateUnitFullName`/`subordinateUnitFullName`) — выгрузка, слияние, снимок и откат затрагивают
только область формы/макета, `Configuration.xml` и остальные файлы владельца не трогаются. Реквизиты,
табличные части, команды, измерения, ресурсы, значения перечислений и колонки по-прежнему адресуются
владельцем — у них нет собственного XML и записи в хранилище. Общие формы/макеты (`CommonForm`/
`CommonTemplate`) — корневые объекты, для них это правило не применяется. Если у узла формы/макета не
удалось определить имя (`label` не задан), `resolveFullName` возвращает `null` без отката на владельца —
команда завершается ошибкой «не удалось сформировать полное имя объекта».

Список подкаталогов подчинённых со своим XML — единственный источник `SUBORDINATE_OBJECT_FOLDERS`
(`infra/fs/SubordinateObjectLayout.ts`); его же использует `SupportInfoService` для определения режима
поддержки BSL-модулей (см. [bsl-language-support.md](./bsl-language-support.md#определение-режима-поддержки-bsl-модуля)).
Раскладка подчинённых для хранилища — `REPOSITORY_SUBORDINATE_LAYOUT` (`infra/repository/RepositoryObjectNames.ts`):

| Тег ChildObjects | Каталог | Имя в `-listFile` / `Objects.xml` |
|---|---|---|
| `Form` | `Forms` | `Справочник.X.Форма.Y` |
| `Template` | `Templates` | `Справочник.X.Макет.Y` |
| `Recalculation` | `Recalculations` | `РегистрРасчета.X.Перерасчет.Y` |
| `Table` | `Tables` | `ВнешнийИсточникДанных.X.Таблица.Y` |
| `Cube` | `Cubes` | `ВнешнийИсточникДанных.X.Куб.Y` |
| `DimensionTable` | `DimensionTables` | `…Куб.Y.ТаблицаИзмерения.Z` |
| `Subsystem` | `Subsystems` | `Подсистема.A.Подсистема.B` |

Корень — `Конфигурация.<Name>` (и для расширения с `-Extension`); в `state.json` он представлен сентинелами
`__configuration_root__` / `__extension_root__`. Имена в трёх алфавитах (fullName хранилища, ссылка
ChildObjects/ConfigDumpInfo, путь выгрузки) переводятся только в `RepositoryObjectNames` и
`RepositoryObjectScope`. Несуществующее в базе имя в `-listFile` роняет **всю** выгрузку — поэтому имена
подчинённых берутся только из источника, соответствующего базе.

### Области файлов

`ObjectScope` (`RepositoryObjectScope.ts`) — набор файлов единицы:

- `unit` — XML единицы и её каталог **без** каталогов подчинённых единиц (Forms, Templates, …). Слияние,
  снимки и сравнение работают только с этой глубиной.
- `tree` — весь каталог. Только для единиц, удалённых из хранилища, и старых («глубоких») снимков.
- `root` — `Configuration.xml` + корневой `Ext/**`; `all` — вся конфигурация (запасная полная выгрузка).

Файлы подчинённых, не участвующих в операции, не входят в область — они не перезаписываются и не удаляются.

## Потоки и блокировка Конфигуратора

Потоки — `ui/commands/repository/RepositoryLockSync.ts` (захват/получение) и `RepositoryUnlockSync.ts`
(отмена/помещение), эталоны отмены — `RepositoryUnlockEtalons.ts`. Все внешние точки (CLI, выгрузка,
диалоги) внедряются через `RepositoryFileSyncDeps` (`RepositoryFileSyncShared.ts`).

1. `ensureRepositoryGuardFree` — занятость `ConfigurationOperationGuard` проверяется **до** первого
   QuickPick; при занятости — лог `[repository][file-sync][busy] … "<heldBy>"` и `notifyBusy` без `await`.
2. Хеш-кэш (и для рекурсивного корня — хеши файлов проекта) читается до аренды.
3. **Одна аренда** `runExclusive`: CLI хранилища → `applyLock`/`applyUnlock` → выгрузка во временный каталог.
   Внутри аренды нет диалогов и `await vscode.window.show*` (запрет №18).
4. После аренды: слияние, единственный модальный диалог, запись файлов, снимки, post-mutation, сообщения.

Остальные команды хранилища — `connect`/`create`/`disconnect`/`addUser`/`copyUsers`/`dump`/`report`/`setLabel`
(issue #40) — тоже запускают Конфигуратор на базе проекта и сериализуются тем же guard'ом:
`requireFreeRootTarget` (`RepositoryCommands.ts`) проверяет занятость до форм и диалогов, а
`runRepositoryCliCommand` запускает процесс под арендой с заголовком `progressTitle` (например,
«Отчёт по хранилищу: <имя>»). Сообщения об исходе и `afterSuccess` — после `release()`; синхронизация с базой
после подключения (`runPostRepositorySync`) берёт guard отдельной арендой.

Выгрузка никогда не пишется сразу в проект: временный каталог → план слияния → применение.
`ConfigDumpInfo.xml` частичной выгрузкой не создаётся; проектный заменяется только после успешного
root-incremental.

### Раунды выгрузки (`RepositoryDumpRounds.ts`)

Оптимистичная схема: в обычном случае **один** запуск Конфигуратора.

1. Раунд 0 — якоря операции плюс замыкание раскрытия по **проектному** XML; не-якорные имена берутся, только
   если XML единицы есть в хеш-кэше (единица известна базе).
2. Раунд 0 упал (в списке имя, которого уже нет в базе) → повтор только якорями.
3. Раунды 1…N — раскрытие новых найденных единиц по их XML **из выгрузки** (версия хранилища); пусто — стоп.
   Предел `MAX_DUMP_ROUNDS = 5` по всем запускам; недовыгруженные единицы → `missing`: в слияние не входят,
   их файлы не трогаются, после аренды — предупреждение «выполните повторно».

Стратегии раскрытия: `subordinates` (рекурсивная операция над объектом; куб — ещё уровень таблиц измерения),
`subsystem` (рекурсивная подсистема: вложенные подсистемы, участники `<Content>` и их подчинённые —
`SUBSYSTEM_MEMBERS_INCLUDE_SUBORDINATES = true`, т.к. рекурсивный захват подсистемы захватывает формы
участников), `new-subordinates` (нерекурсивная операция: только подчинённые, которых нет в проекте —
платформа довозит новые формы и при нерекурсивном захвате/получении, но не захватывает их), `towards`
(отмена без снимка), `none` (root-incremental: точные имена, один раунд).

### Рекурсивный корень (root-incremental)

`-configDumpInfoOnly` во временный каталог → `diffConfigDumpInfo(проектный, новый, extractDumpInfoUnit)` по
единицам (`Catalog.X.Form.Y.Form` → `Catalog.X.Form.Y`) → частичная выгрузка только изменённых и добавленных
единиц. `configVersion` меняется только у полученных единиц, поэтому повтор без изменений не запускает
вторую выгрузку. Полная выгрузка во временный каталог — запасной путь: нет проектного `ConfigDumpInfo.xml`,
он не разобрался, сбой `-configDumpInfoOnly`, пустой новый файл при непустом проектном, изменено больше
`ROOT_INCREMENTAL_MAX_OWNERS = 400` единиц или больше `ROOT_INCREMENTAL_MAX_SHARE = 50%`.

## Временные файлы и очистка

Раскладка и функции очистки — единственный источник `infra/repository/RepositoryTempCleanup.ts`
(`getRepositoryObjectsDir`/`getRepositoryMergeRoot`). Любое удаление файла/каталога хранилища (снимки,
резервные копии слияния, `objects/*.xml`) идёт только через `removePathWithRetries` (issue #103):
`fs.rmSync` с `recursive: true, force: true, maxRetries: 3, retryDelay: 100` — на Windows
`EPERM`/`EBUSY`/`ENOTEMPTY` при удалении обычно временные (антивирус, индексатор, LSP-сервер держат
файл), повтор снимает большинство таких сбоев без вмешательства пользователя. Примитив удаления —
тип `RemoveTree`, внедряется через конструктор (`RepositoryLockSnapshotStore`, опция `removeTree` в
`RepositoryService`) — точка подмены для тестов, имитирующих неудаляемый файл. Сообщения об оставшихся
сбоях строятся через `describeFsError`: в сообщение идёт код ошибки ФС (`'EPERM'`), а не
`error.message` — у `fs`-ошибок Windows путь в `message` приходит в неверной кодировке; сам путь
вызывающий код подставляет из `resolve*()`-геттеров хранилища, а не из исключения.

- `.v8vscedit/repository/objects/<scope>-<ts>.xml` — `Objects.xml` для `-ObjectsFile` живёт только на
  время одного запуска Конфигуратора: `runSubjectCli` (`RepositoryFileSyncShared.ts`) удаляет его в
  `finally` при любом исходе, включая исключение. Дополнительно первым шагом каждой аренды
  `runRepositoryExclusive` → `sweepRepositoryTempArtifacts` подметает все `objects/*.xml` — это
  безопасно, т.к. такие файлы создаются только внутри аренды общего guard'а хранилища (ограничение —
  один процесс расширения на рабочую область, см. «Известные ограничения», issue #77).
- `.v8vscedit/repository/merge/<scope>/<stamp>-<label>/` — резервные копии перезаписываемых/удаляемых
  файлов и копии версии хранилища для сравнения при `keep-local` (в т.ч. единственная копия отброшенных
  правок при отмене захвата). Ротация — в начале аренды, `pruneMergeBackups`: удаляется каталог старше
  `DEFAULT_MERGE_BACKUP_RETENTION.maxAgeMs` (7 дней) или сверх `maxPerScope` (20) последних в своём
  scope; возраст берётся из метки времени в имени каталога, а не из mtime (копирование/распаковка
  рабочей области mtime меняют). Каталоги с неразборчивым именем и метки из будущего (сбитые часы) не
  трогаются и в лимит не считаются; опустевший каталог scope удаляется. Цена ротации: открытые вкладки
  сравнения на уже удалённую резервную копию покажут «файл не найден».
- Сбой любого шага очистки не срывает операцию, ради которой взята аренда, — в журнал «1С Редактор»
  идёт строка `[repository][file-sync][warn] очистка временных файлов не удалась: …`.
- Снимки захвата (`.v8vscedit/repository/snapshots/`) удаляются при отмене захвата и при помещении без
  `keepLocked`; дополнительно — при отключении хранилища (`clearBinding`) и при новой привязке
  (`saveBinding`), обе точки вызывают `discardAll(target)`.
- Каталоги выгрузки `.v8vscedit/import-temp/repository-dump-*` освобождаются и при исключениях —
  `disposeOnError`/`disposeOnErrorAsync` (`RepositoryTempCleanup.ts`) оборачивают код между выгрузкой во
  временный каталог и передачей владения им вызывающему.
- Хвосты после аварийного завершения самого процесса расширения (issue #76) подметает
  `sweepStaleOperationTemp` (`infra/process/StaleOperationTempSweep.ts`) при активации расширения
  (`Container.bootstrap`, асинхронно, без ожидания): каталоги `.v8vscedit/import-temp/*` (все префиксы
  `createImportTempDir` — `repository-dump-`, `import-ext-`, `import-cf-`, `list-ext-`; возраст по mtime,
  т.к. в имени `mkdtemp` метки нет; `infra/fs/WorkspaceTempDir.ts`) и одноразовые выгрузки агента
  `.v8vscedit/agent/0/workspace/<ключ>-dump-<мс>-<номер>` с `lists/<то же>.txt` (возраст по метке в имени;
  имя строит и разбирает только `infra/agent/AgentDumpCleanup.ts`, постоянное зеркало `workspace/<ключ>` не
  трогается). Подметание идёт вне аренды guard'а — слияние и диалог конфликта держат каталог выгрузки и после
  неё, — поэтому живой поток защищает только порог `STALE_OPERATION_TEMP_MAX_AGE_MS` (сутки, строго больше);
  метки из будущего не трогаются. Сбой шага — строка `[init][warn] очистка устаревших временных каталогов не
  удалась: …` в журнале «1С Редактор», активация не срывается.

### Диалоги команд

`RepositoryCommandDialogs.ts` — единственный источник диалогов хранилища: `askRecursiveMode`,
`pickUnlockForce`, `pickDisconnectForce`, `promptRepositoryVersion`,
`validateRepositoryVersion`. У пунктов QuickPick заполнены `description`/`detail`; первым идёт безопасный
вариант (без `-force` / только выбранный объект / штатное отключение), второй — с побочными эффектами.

- **Рекурсия** (`askRecursiveMode`) спрашивается только если `RepositoryService.canApplyRecursively(node)`
  вернул `true`: для корня конфигурации/расширения и подсистемы — всегда (состав по `<Content>`/составу
  конфигурации не определить статически), для прочих узлов — по `<ChildObjects>` XML единицы (для
  подчинённой единицы — её собственный XML по полному имени, т.к. `xmlPath` узла формы/макета в дереве —
  XML владельца; для остальных child-like узлов — XML владельца) есть ли теги из
  `REPOSITORY_SUBORDINATE_TAGS` (`infra/repository/RepositoryObjectNames.ts` — производное множество ключей
  `REPOSITORY_SUBORDINATE_LAYOUT`, тем же множеством теперь фильтруются раунды выгрузки в
  `RepositoryDumpRounds.ts`). Нечитаемый или неизвестный XML — вопрос всё равно задаётся (см.
  `canApplyRecursively`). Если вопрос не задан, `recursive = false` — это безопасно: платформа довозит
  новые подчинённые и при нерекурсивной операции (стратегия раскрытия `new-subordinates`), просто не
  захватывает их.
- **`unlock` с `-force`** (`pickUnlockForce`) — проверено на стенде (план §10.12): без ключа Конфигуратор
  завершается с rc=1 «Объект … был изменён» и ничего не освобождает; с ключом объект в базе возвращается к
  версии хранилища.
- **`update`/`updateToVersion` — `-Force` всегда, без вопроса** (issue #80). На стенде 8.5.1 ключ не меняет
  результат: без него новые объекты добавляются, удалённые удаляются, захваченный и локально изменённый
  объект не перезаписывается — ни с ключом, ни без (план §10.12). Конфигуратор сам дополняет состав
  («Для выполнения операции требуется получение объектов» → отмена → повтор с расширенным составом, rc=0).
  По документации платформы ключ подтверждает получение новых и удаление объектов — передаётся как
  страховка для других версий платформы (8.3.27 не проверялась).
- **`disconnect` с `-force`** (`pickDisconnectForce`) — проверено на стенде: без ключа при захваченном
  изменённом объекте отказ «Обнаружены захваченные объекты, измененные в конфигурации», с неверным паролем —
  ошибка аутентификации; с ключом база отключается и с неверным паролем, и без параметров хранилища. Захваты
  пользователя при этом остаются на сервере, из отключённой базы их не снять.
- `repository.update` больше не спрашивает номер версии — всегда получает актуальную (без `-Version`).
  Номер версии спрашивает отдельная команда узла `v8vscedit.repository.updateToVersion` («Получить версию
  из хранилища…», иконка `history`, в контекстном меню сразу после `repository.update` при
  `-repoConnected`): `promptRepositoryVersion` (натуральное число без ведущих нулей, `validateRepositoryVersion`)
  → рекурсия → тот же поток `runRepositoryUpdateFlow` с `-Version` и `-Force`.

## Трёхстороннее слияние

`RepositoryMergePlanner.ts` (чистый план) и `RepositoryMergeApplier.ts` (применение). Для каждого файла
области: **R** — версия хранилища (выгрузка), **L** — локальный файл, **B** — база (хеш-кэш, для файлов вне
кэша — снимок).

| Состояние | Действие |
|---|---|
| L == R | ничего |
| L == B (или нет ни L, ни B) | записать молча |
| прочее при наличии R | конфликт-запись |
| нет R, L == B | удалить молча |
| нет R, L ≠ B | конфликт-удаление |
| файл открыт с несохранёнными правками | всегда конфликт |

При конфликтах — **один** модальный диалог на операцию: «Сравнить» / «Заменить из хранилища»; Esc = «оставить
локальное» (`keep-local`):

- **Заменить / Сравнить** — локальная версия сначала уходит в бэкап
  `.v8vscedit/repository/merge/<scopeKey>/<время>-<метка>/<rel>`, затем файл перезаписывается побайтово
  (BOM/EOL версии хранилища). «Сравнить» открывает до `MAX_DIFF_TABS = 10` окон единой конвенции сторон
  (слева всегда локальное состояние, справа — версия хранилища): бэкап моих правок слева ↔ файл проекта
  (уже перезаписан версией хранилища) справа, `projectSide: 'repository'` (только текстовые файлы, остальные
  — в журнал).
- **Esc** (`keep-local`) — конфликтные файлы не трогаются; версия хранилища кладётся в `…/merge/…/repository/<rel>`,
  хеш в кэше = хеш хранилища (файлы помечаются изменёнными), немодальное сообщение с кнопкой «Сравнить»:
  файл проекта (мои изменения) слева ↔ копия хранилища справа, `projectSide: 'local'`.

Заголовок окна — `formatMergeDiffTitle` (`RepositoryFileSyncDialogs.ts`): `<basename> (мои изменения: копия ↔
хранилище: файл проекта)` при `projectSide: 'repository'`, `<basename> (мои изменения: файл проекта ↔
хранилище: копия)` при `projectSide: 'local'` — по подписи видно, какая сторона это файл проекта и её можно
редактировать. Пара для окна — `MergeDiffPair { title, local, repository, projectSide, writable }`
(`local`/`repository` — абсолютные пути сторон, `mergeDiffProjectPath(pair)` возвращает путь файла проекта);
`writable` (объект захвачен, поддержка разрешает редактирование) и существование файла определяются только по
файлу проекта, а не по резервной копии/копии хранилища.

Перед записью хеш локального файла перепроверяется (правка между планом и применением → бэкап). После
применения хеш-кэш = состояние базы. Новые объекты верхнего уровня добавляются в `ChildObjects`
`Configuration.xml` через `ConfigurationXmlEditor` (`ConfigurationChildObjectsSync.ts`).

Post-mutation: `suppressConfigurationReloadForFiles` → запись и патч хеш-кэша → `markChangedConfigurationByFiles`
для оставленных расхождений → структурные изменения ⇒ `reloadEntries()`, иначе
`treeProvider.refreshCacheForFiles` → `refreshActionsView()`. `changeDetector.detect()` не вызывается.

## Снимки и отмена захвата

`RepositoryLockSnapshotStore.ts`, раскладка
`.v8vscedit/repository/snapshots/<scopeKey>/<sha1(fullName)>/{manifest.json,files/<rel>}`.
Публичные `resolveScopeDir(target)`/`resolveSnapshotDir(target, fullName)`/
`resolveRootManifestPath(target)` — единственный источник этих путей (используются и самим хранилищем,
и `RepositorySnapshotSteps.ts` для сообщений об ошибках).

- Снимок = ровно версия хранилища, по одному на захваченную единицу. Манифест v3:
  `{version: 3, files, hashes, depth: 'unit'|'tree', subordinates?}`; v1/v2 читаются как `depth: 'tree'`.
- Рекурсивный корень вместо снимков хранит хеш-манифест `root-manifest.json` (без копий файлов). Файлы,
  оставленные при keep-local, фиксируются в нём хешем хранилища; оставленные локальные файлы, которых в
  хранилище нет, в манифест не попадают — при отмене они считаются расхождением.
- Получение пересоздаёт снимки только захваченным единицам; помещение с `keepLocked` снимает снимок из
  проекта; без `keepLocked` снимки удаляются.
- **Инвалидация снимка — «manifest-first» (issue #103).** Перед перезаписью снимка (или при `discard`)
  `manifest.json` удаляется первым и пишется последним; недоснятый каталог без манифеста снимком не
  считается. Если удалить каталог целиком не удалось (но манифест удалить получилось), эталоном при
  следующей отмене захвата служит не устаревший снимок, а свежая выгрузка версии хранилища (`towards`) —
  см. «Эталон при отмене» ниже.

### Шаги снимков — best-effort (issue #103)

Снимок — вспомогательный эталон для отката, а не часть самой операции хранилища: сбой его записи/удаления
(на Windows чаще всего `EPERM`/`EBUSY` от антивируса или индексатора) не должен рвать уже выполненный
захват/получение/отмену/помещение. `ui/commands/repository/RepositorySnapshotSteps.ts` оборачивает
каждый шаг снимка (`captureUnitSnapshotStep`, `captureRootManifestStep`, на их общей основе
`trySnapshotStep`):

- сбой шага пишется строкой `[repository][file-sync][warn]` в журнал «1С Редактор» и не выбрасывается
  дальше — поток продолжает выполнение (запись `state.json`, показ окон сравнения/резервных копий,
  итоговое уведомление, обновление дерева) как при успехе;
- в конце потока одно немодальное сводное предупреждение — `reportSnapshotFailures` (число несохранённых/
  неудалённых снимков, подробности — в журнале);
- если после сбоя записи снимка манифест всё ещё читается — значит, не удалось удалить даже
  `manifest.json` прошлого захвата (`isStale` в `captureUnitSnapshotStep`/`captureRootManifestStep`),
  и предупреждение получает отдельный текст: «снимок прошлого захвата устарел — откат при отмене
  захвата вернёт его версию, удалите каталог вручную: `<путь>`» — это единственный случай, когда сбой
  снимка меняет поведение будущей отмены захвата (см. «Известные ограничения»).
- при захвате/получении (`completeFetchSync`, `RepositoryLockSync.ts`) сбой снимка **после** успешного
  слияния не должен скрыть окна сравнения конфликтов и путь резервных копий — они показываются
  (`reportMergeOutcome`) независимо от исхода снимка, предупреждение о снимках идёт отдельно; если
  ошибка происходит уже после того, как файлы проекта переписаны, `reportBackupsAfterFailure`
  дополнительно сообщает путь каталога резервных копий, чтобы прежние версии не потерялись из виду;
- при отмене захвата (`rollbackToEtalons`, `RepositoryUnlockSync.ts`) тот же принцип: сбой самого отката
  (переписывания/удаления файлов) сообщает путь резервных копий тем же `reportBackupsAfterFailure`,
  а сбой пересъёма снимка после помещения с `keepLocked` — тем же `reportSnapshotFailures`.

Эталон при отмене (`RepositoryUnlockEtalons.ts`), единицы обходятся от предков к потомкам: покрыта предком с
`tree` → пропуск; свой снимок → эталон-снимок; у предка снимок v3 с `subordinates` без этой единицы (создана
локально) → эталон «пусто» без Конфигуратора; иначе — выгрузка в той же аренде (`towards`). Рекурсивный корень
сравнивает текущие хеши с манифестом (или хеш-кэшем) и выгружает только изменившиеся единицы; изменений нет —
Конфигуратор не запускается.

Расхождения с эталоном → модальный «Откатить к версии хранилища» / «Оставить изменения» (Esc = оставить).
Откат делает бэкап каждого перезаписываемого и удаляемого файла, удаляет лишние файлы области. При обоих
исходах хеш-кэш = эталон, оставленные файлы помечаются изменёнными.

## Состояние захватов (`state.json`)

`.v8vscedit/repository/state.json`, формат `version: 2` (`RepositoryLockState.ts`). Необязательные поля цели:
`rootRecursive`, `releasedUnderRoot`, `lockGroups` (якорь → состав рекурсивного захвата), `lockModes`
(`'recursive' | 'object'` — режим последнего захвата единицы). Некорректные значения при чтении отбрасываются.
`RepositoryLockRequest.refused` (issue #87, см. «Частичный отказ рекурсивного захвата» выше) — единицы,
в захвате которых сервер отказал в той же операции: `applyLock` их не пишет в `lockedFullNames`/
`lockGroups`, а при рекурсивном захвате корня — дописывает в `releasedUnderRoot`.

`isLocked(target, unit)` = явно захвачена ИЛИ участник группы ИЛИ под рекурсивным корнем и не освобождена ИЛИ
(правило старых записей) захвачен предок без записи в `lockModes`. Нерекурсивная отмена якоря группы снимает
только якорь — на сервере подчинённые остаются захваченными.

`applyUnlock` удаляет освобождённую единицу из **всех** `lockGroups`, а не только из группы своего якоря:
сервер освобождает её безусловно, поэтому запись не должна остаться участником чужой группы. Пример: при
рекурсивном захвате справочника форма входит в группу владельца; отмена захвата формы убирает её из этой
группы — владелец и остальные формы остаются захваченными, форма — нет.

Три необязательных поля для статусов с сервера (issue #6, `RepositoryLockState.ts`): `foreignLocks` (кто
и когда захватил чужой объект — из опроса или из отказа захвата), `serverOwnLocks` (захваты нашего
пользователя по данным сервера, в т.ч. сделанные вне проекта) и `lockSync` (метка последнего опроса:
время, пользователь, версия сервера рукопожатия). Формат `state.json` остаётся `version: 2` — поля
необязательны, старые файлы читаются без изменения поведения; мусорные значения при чтении отбрасываются
(`sanitizeScope`), пустые поля не пишутся (`compactScope`).

**Чужой захват перекрывает свой.** `isLocked`/`isRootLocked` возвращают `false`, если объект есть в
`foreignLocks`, даже при локальной записи или рекурсивном корне: сервер уже отдал объект другому
пользователю, локальная запись и снимок при этом не удаляются — раздел «Снимки и отмена захвата» не
меняется, конфликт решает пользователь штатными командами.

**Захват своего пользователя вне проекта не идёт в `lockedFullNames`.** Если опрос находит захват НАШЕГО
пользователя, которого нет в локальном кэше (сделан в Конфигураторе или в другой базе), запись остаётся
только в `serverOwnLocks` — `getLockInfo` даёт `own-elsewhere`, узел остаётся `-repoUnlocked` и только для
чтения. Причина: у объекта нет снимка `RepositoryLockSnapshotStore`, а файлы проекта могут отличаться от
версии хранилища — добавление в `lockedFullNames` без снимка сделало бы помещение перетирающим чужие
правки, а отмену захвата — откатом без эталона. Штатный «Захватить» с `-revised` «усыновляет» такой
объект: создаёт снимок и добавляет запись без потери файлов.

## Статусы захватов с сервера

Issue #6. `RepositoryLockStatusService.syncTarget(target)` (`infra/repository/RepositoryLockStatusService.ts`)
опрашивает актуальные захваты хранилища и заменяет ими `foreignLocks`/`serverOwnLocks` цели в `state.json`
— в дополнение к локальному потоку захвата/отмены/помещения из разделов выше. Источник данных зависит от
вида хранилища, но модель и UI от него не зависят (`RepositoryLockStatusSource` — общий интерфейс,
`supports(location)` выбирает подходящий):

- **Файловое хранилище** — прямое чтение `1cv8ddb.1CD` (`infra/repository/onecd/OneCdFile.ts` +
  `OneCdTable.ts`): постранично read-only, без запуска платформы. Формат — только `1CDBMSV8` версии
  `8.3.8.0`; захваченность объекта — `USERS × OBJECTS` по `REVISED = true`, держатель — `USERS.NAME` по
  `REVISORID`, время — `REVISEDATE` (локальное, без зоны).
- **Сетевое хранилище** (`tcp://`, `http://`, `https://`, схема без учёта регистра) — метод
  `DevDepot_devObjectsStatistic` протокола crserver (`infra/repository/crs/` + `infra/xml/CrsMessageXml.ts`),
  без запуска платформы и без `<crs:bind>` (запрос только читает статистику, `<crs:objRefs/>` — все
  объекты). Адресация: для http(s) alias — сегмент пути после `.1ccr`, по умолчанию `maincr`
  (`parseCrsAddress`, `CrsAddress.ts`); для tcp alias — весь путь после хоста без крайних слэшей
  (`tcp://host/a/b` → alias `a/b` — так его передаёт сам Конфигуратор, проверено снятым запросом).

В обоих случаях OBJID/uuid объекта на сервере сопоставляется с полным именем через `ConfigDumpInfo.xml`
цели (`parseConfigDumpInfoUnitIds` + `dumpInfoOwnerToRepositoryFullName`) — отдельного реестра GUID-классов
1С нет; объекты, которых нет в выгрузке проекта, считаются в `unmatched` и пропускаются.

**Рукопожатие по версии (только сеть).** Первый вызов идёт с версией-подсказкой по приоритету: версия
сервера последнего успешного опроса (`lockSync.serverVersion`) → `--v8version`/`--path` из кэша `env.json`
(`RepositoryBindingStore.readPlatformVersionHint()`) → константа `DEFAULT_CRS_VERSION_HINT`. При
`call_exception` «несоответствие версий» — ровно один повтор с версией сервера из исключения
(`CrsClient.callCrs`, не больше двух вызовов). Общий таймаут — 60 с (подключение + ответ), лимит размера
ответа — 128 МиБ, проверяется и по `Content-Length`, и по фактически принятым байтам
(`CrsTransport.ts`). Ошибки crs (неверный пароль, неверный alias, TLS, обрыв кадрирования tcp,
превышение лимита и т.д.) не бросают исключение наружу — `syncTarget` всегда возвращает
`{status:'failed', code, reason}`.

**Опрос при старте.** `Container.bootstrap()` после `reloadEntries()` вызывает
`syncRepositoryLockStatusesOnStartup` (`void`, без ожидания) по всем подключённым целям — **только если
`vscode.workspace.isTrusted`**: это сетевой вызов с учётными данными, подложенный `env.json` в недоверенной
рабочей области увёл бы хеш пароля на чужой сервер. Исходы идут только в лог `[repository][locks]`, без
уведомлений; дерево обновляется, только если состояние изменилось. Команда узла
`v8vscedit.repository.refreshLocks` («Обновить статусы захватов», иконка `refresh`) — в контекстном меню
корня при `-repoConnected` (`UniversalPanelViewProvider.addRepoRootActions`) — делает то же самое по
запросу, но с немодальными уведомлениями (`RepositoryLockStatusCommands.ts`).

**Отметка чужого захвата по отказу захвата.** При `failed` в потоке `lock` (`RepositoryLockSync.ts`) строки
вида `Объект захвачен для редактирования другим пользователем: <Имя> (<Пользователь>)` из вывода `/Out`
(`RepositoryLockOutputParser.ts`) помечают объект как «захвачен другим: `<пользователь>`» — **только для
объектов, которые пользователь пытался захватить** (`selectAttemptedRefusals`): нерекурсивно — `subject.
members`, рекурсивно — плюс подчинённые единицы членов, рекурсивный корень — любые. Пакетный режим
Конфигуратора не выводит дату захвата — отметка идёт без `lockedAt`, с `observedAt` (моментом отказа);
следующий успешный опрос сервера её заменяет точной датой.

**Частичный отказ рекурсивного захвата (issue #87).** `/ConfigurationRepositoryLock -objects` неатомарен:
при рекурсивном захвате платформа захватывает всё, что может, и завершается с кодом 1, если хотя бы одна
попытанная единица занята другим пользователем. В таком выводе, помимо строк отказа, есть строка
`Объект захвачен для редактирования: <Имя>` по каждой вновь захваченной единице (уже свой захват такой
строки не получает — `RepositoryLockOutputParser.parseRepositoryLockGrants`). `RepositoryLockSync.
summarizePartialLock` разбирает `failed`-вывод потока `lock` через `summarizeRepositoryLockOutput`; если
среди попытанных единиц есть хоть одна `granted`, поток продолжается так же, как при `done`, а не как
при полном отказе:

- `RepositoryLockOutputParser.selectLockedMembers(candidates, summary)` решает, какие единицы записать
  захваченными: `granted` — записываются всегда; `refused` — не записываются, даже если это якорь;
  потомок отказанной единицы без собственной строки успеха — тоже не записывается (у него нет «своего»
  захвата, который мог бы удержаться); прочие кандидаты без строки успеха при незанятом предке
  записываются как раньше — платформа не отмечает строкой успеха только уже наш захват, а не любой
  захват без отказа. Если отказан якорь, а подчинённые захвачены — `isLocked(anchor) = false`,
  подчинённые снимаются собственными записями; группа якоря (`lockGroups`) пишется, только если после
  фильтра отказанных остаётся больше одной записанной единицы.
- `applyLock` получает отказанные единицы полем запроса `RepositoryLockRequest.refused` — они не попадают
  в `lockedFullNames` и в `lockGroups`; при рекурсивном захвате корня (`recursiveRoot`) отказанные
  единицы **дописываются** в `releasedUnderRoot`, а не заменяют его целиком — иначе точечные освобождения
  прежних операций терялись бы. Сентинел корня в `releasedUnderRoot` не пишется (корень не может быть
  «под самим собой» освобождённым исключением).
- Отказанным единицам ставится отметка foreign (`applyLockRefusals`) — тем же механизмом, что при полном
  отказе.
- Выгрузка, слияние и снимки идут только по захваченным единицам: `RepositoryLockSync.
  withoutRefusedUnits` вычёркивает отказанные `fullName` из области слияния (`entries`/`added`) и, при
  частичной (инкрементной) выгрузке рекурсивного корня, не даёт скопировать `ConfigDumpInfo.xml` в
  проект — иначе базовая линия сдвинулась бы на версии отказанных единиц, чьи файлы не слиты, и следующий
  инкремент перестал бы видеть их изменёнными. При полной выгрузке (область `all`) фильтра нет: она
  описывает конфигурацию целиком, а не единицу, и отказанные единицы получают версию хранилища как часть
  этой выгрузки (осознанное решение — здесь диалог конфликта — штатный путь).
- Поток возвращает `'done'`, а не `'failed'`; пользователю — один warning со списком
  `<fullName> (<пользователь>)` вместо info-сообщения об успехе, в журнал «1С Редактор» —
  `[repository][locks] частичный захват «<метка>», объекты захвачены другими пользователями: …`. Если
  строк успеха в выводе нет вообще (`summarizePartialLock` вернул `undefined`) — поведение прежнее:
  `'failed'`, отметка foreign через `recordLockRefusals` (тот же путь, что до issue #87).
- Поток `update` частичный отказ не разбирает: `summarizePartialLock` вызывается только для `operation
  === 'lock'` — получение не меняет состояние захвата, и код 1 для него остаётся полным отказом.

## Readonly

`RepositoryService.isEditRestricted(filePath)` определяет единицу по пути (только строковые операции) и
требует её захвата: при нерекурсивном захвате справочника файлы форм и макетов остаются только для чтения
(на сервере они не захвачены — загрузка их в базу была бы отклонена), при рекурсивном — редактируемы.
Файлы корня (`Configuration.xml` и корневой `Ext/**`: модули приложения, сеанса и т.п.) XML владельца не
имеют — они требуют захвата корня (`isRootLocked`), как узел корня в дереве (issue #55). Поэтому свойства
«Конфигурация» в панели свойств и MCP, модули корня и сторона проекта в окне слияния без захвата корня —
только для чтения. `ConfigDumpInfo.xml` не единица хранилища и не ограничивается.
`EditorReadonlyController` (`ui/readonly/`) подписан на `onDidChangeLocks` и по чистому плану
`planReadonlyTransitions` переключает readonly открытых вкладок (включая обе стороны диффа) без
переоткрытия: видимые — сразу, скрытые — при активации. Вкладки служебного `.v8vscedit/`
(`isInsideWorkspaceServiceDir`, `infra/fs/WorkspaceTempDir.ts`) в план не попадают (issue #79): когда корень
конфигурации совпадает с корнем рабочей области, бэкапы и копии слияния `.v8vscedit/repository/merge/**`
лежат внутри него, но файлами конфигурации не являются.

Несохранённый документ (`isDirty`) в readonly не переводится (issue #62): readonly сессии запрещает
сохранение, и после отмены захвата правки можно было бы только потерять («Не сохранять» при закрытии).
План кладёт такой переход в `afterSave`, контроллер держит документ в ожидании и применяет readonly, когда
документ становится чистым — после сохранения или отката (`onDidChangeTextDocument` приходит и при смене
`isDirty`): видимая вкладка — через очередь, скрытая — при активации. Снятие readonly (захват) применяется к
несохранённому документу сразу; новое событие захватов и закрытие документа отменяют ожидание.
То же при открытии (issue #81): `BslReadonlyGuard` не ставит readonly несохранённому документу — например,
буферу, восстановленному hot exit после перезапуска, — а публикует `onDidSkipDirty`, и контроллер ставит
документ в то же ожидание. Признак проверяется в момент применения, а не в `onDidOpenTextDocument`.

Readonly-команды VS Code (`set/resetActiveEditorReadonlyInSession`, `ui/readonly/sessionReadonly.ts`)
действуют только на основную (правую) сторону активного редактора; сам readonly-флаг хранится по ресурсу, а
не по вкладке, поэтому левая file:-сторона сравнения редактируема, если её ресурс не readonly. Для файла
проекта, открытого только левой стороной сравнения, `selectReadonlyApplyRoute`
(`ui/readonly/readonlyTabSelection.ts`) выбирает один из трёх маршрутов применения (`runWithResourceActive`):
- `activate` — есть видимая основная (не-левая) вкладка ресурса — активируется без побочных эффектов;
- `temporary` — ресурс открыт только левой стороной сравнения: временная обычная вкладка (`preview: false`),
  команда readonly, затем вкладка закрывается (если не была открыта раньше и документ не dirty), сравнение
  переоткрывается, если было видимо;
- `defer` — только скрытая основная вкладка — переход откладывается до её активации, как раньше.

Левая сторона сравнения переходит сразу, минуя `pending`-очередь скрытых вкладок
(`isImmediatelyApplicable` в `readonlyTabSelection.ts`): в VS Code событие активации сравнения приходит по
правой стороне, поэтому отложенный переход левой стороны никогда бы не выполнился. `runWithResourceActive`
выполняет команду readonly только если после активации ресурса активным остался именно он (`applyIfActive`)
— иначе команда переключила бы readonly не того файла; после всех переходов исходная активная вкладка
восстанавливается, включая diff-вкладку. В журнал «1С Редактор» идёт `[readonly][skip] активен не <файл>`
при пропуске и `[readonly] временная вкладка оставлена (несохранённые изменения): <файл>`, если временную
вкладку не удалось закрыть из-за несохранённых правок.

Окно сравнения слияния (`openMergeDiffs`, `RepositoryFileSyncDialogs.ts`) тем же маршрутом явно выставляет
readonly файла проекта в обе стороны (issue #78): `writable` — `reset…ReadonlyInSession`, иначе
`set…ReadonlyInSession` — иначе незахваченный файл, не открывавшийся раньше, был бы редактируем в сравнении.
Исход, отличный от применения, через `describeActivationOutcome` пишется в журнал синхронизации
(`deps.openDiffs(pairs, log)` → `[repository][file-sync] [readonly]…`): при `skipped` readonly файла проекта
остаётся прежним.

Дерево (`MetadataTreeProvider.resolveRepositoryState`), панель свойств
(`ui/views/properties/propertyEditLock.ts:resolveRepositoryEditProbePath`) и MCP-шлюз
(`McpMutationGate.assertNodeContentEditable`) проверяют захват формы/макета по **её собственному**
дескриптору (`Forms/Y.xml`/`Templates/Y.xml`), а не по владельцу — `isSubordinateUnitNode`
(`RepositoryService.ts`) применяет то же правило, что и `resolveFullName`/`buildSubordinateUnitFullName`.
Если у узла нет собственного XML-дескриптора (общая для дерева проверка не нашла форму/макет владельца
через `findObjectXmlInFolder`) — откат на проверку по XML владельца, как раньше. Операции, меняющие
СОСТАВ владельца (добавление/удаление/переименование формы, `add_form`/`remove_form`/`remove_metadata`/
`rename_metadata`), по-прежнему проверяются через `assertNodeEditable`/`isMetadataEditRestricted` по
владельцу — состав хранится в `ChildObjects` владельца, а не в самой единице.

## Настройка

`v8vscedit.repository.syncFilesOnLockUnlock` (по умолчанию `true`) включает выгрузку, слияние, снимки и откат.
Захват с `-revised`, guard, состояние захватов и readonly работают всегда. MCP-инструмента нет: команды
`v8vscedit.repository.*` не входят в `ALLOWED_COMMANDS` моста `v8vscedit_execute_command` — все пять операций
(`lock`/`update`/`updateToVersion`/`unlock`/`commit`) требуют интерактивных решений пользователя (рекурсия,
конфликты, откат, номер версии). По той же причине без MCP-инструмента и `v8vscedit.repository.refreshLocks`
(issue #6): хотя команда не интерактивна и не требует диалогов, она меняет только локальный кэш
`state.json`, а не конфигурацию или базу — MCP-поверхность полагается только на операции, что-то реально
меняющие в проекте или базе (см. правило в `CLAUDE.md` о MCP-инструменте для мутирующих команд).

## Известные ограничения

- Повторный захват `-revised` уже захваченного объекта перетирает в **базе** непомещённые правки версией
  хранилища (поведение платформы); локальные файлы защищает слияние, а оставленные правки помечаются
  изменёнными и уйдут в базу следующим импортом.
- Старые записи `state.json` (без `lockModes`) трактуются как раньше: захват владельца делает редактируемыми и
  файлы подчинённых. Запись становится точной после следующего захвата/отмены.
- Хеши файлов корня при отмене рекурсивного захвата корня считаются до аренды синхронно по всей конфигурации;
  правки, сделанные во время самой операции, в сравнение не попадают.
- При событии захвата видимые вкладки корневых файлов (`Configuration.xml`, `Ext/*.bsl`) переактивируются даже
  при захвате другого объекта — кратковременное переключение фокуса.
- Пустые каталоги-контейнеры (`Forms/`) после удаления последней формы остаются.
- Удаление подчинённого объекта в хранилище при нерекурсивном получении платформой не проверено; такие файлы
  не трогаются, в журнал пишется предупреждение.
- Режим поддержки перерасчётов/таблиц/вложенных подсистем берётся от владельца, а не от самой единицы
  (issue #47).
- Тесты вложенных подсистем временно на синтетике, «удалённая в хранилище форма» — правкой копии реального XML:
  ждут фикстуры F1/F4 (issue #48).
- Подметание `objects/*.xml` в начале аренды (`sweepRepositoryTempArtifacts`) исходит из того, что на
  рабочую область работает один процесс расширения; параллельный второй процесс той же рабочей области
  не учтён (issue #77).
- Хвосты временных каталогов после аварийного завершения процесса расширения подметаются только при
  следующей активации и только старше суток: до этого они занимают место на диске (issue #76).
- Применение readonly к левой стороне сравнения (в т.ч. скрытого) кратковременно открывает временную
  обычную вкладку файла проекта в той же группе — побочный эффект маршрута `temporary` в
  `selectReadonlyApplyRoute`/`runWithResourceActive` (`ui/readonly/`).
- Не проверено, применяет ли платформа `-revised` к единицам, захваченным при коде 1 частичного
  рекурсивного захвата (issue #87): фикстуры `2.21-partial-locks`/`2.21-partial-root` проверяют состав
  захвата и состояние `state.json`, но не то, помечены ли захваченные объекты «изменёнными» в самой базе
  так же, как при обычном захвате с `-revised`.
- Сетевой обмен со crserver **8.3.27** вживую не проверен: байты приветствия/кадрирования/ответа сняты
  только с 8.5.1 (сервер 8.3.27 в момент разработки не был установлен), клиентское приветствие
  (`CRS_TCP_CLIENT_HELLO`) и терминатор кадра — константы этой съёмки; байты приветствия сервера не
  валидируются. Фикстур для 8.3.27 в `example/repository/2.21-locks/8.3.27/{tcp,http}` нет — только 1CD и
  `lock-refused.out.txt`. Если реальный обмен 8.3.27 будет снят, тесты сети параметризуются и по нему; до
  этого расхождение (если оно есть) проявится как отказ рукопожатия/кадрирования, а не молча (issue #6).
- Формат 1CD версии, отличной от `8.3.8.0` (в т.ч. старый `8.2.14`), не поддерживается —
  `OneCdFile.open` даёт `unsupported-version`; реальных файлов такой версии для теста нет.
- Ветка `fatlevel=1` (индексные страницы, актуально примерно с 250 тыс. объектов в таблице) в
  `OneCdFile`/`OneCdTable` реализована, но не покрыта тестами на реальном файле — фикстур такого размера
  нет; закрыта `/* c8 ignore */` с обоснованием.
- Сбой удаления снимка best-effort (issue #103): если не удалось удалить даже `manifest.json` прошлого
  захвата, в `.v8vscedit/repository/snapshots/` остаётся устаревший снимок, а `state.json` это никак не
  отмечает — следующая отмена захвата откатит к его (уже неактуальной) версии хранилища. Пользователь
  получает явное предупреждение с путём каталога, который нужно удалить вручную; автоматического
  повторного удаления при следующей операции нет.
- Служебный каталог `.v8vscedit` (снимки, резервные копии слияния, временные выгрузки) попадает в
  область наблюдения LSP-watcher — не исключён явно (issue #104, не сделано в рамках #103).

### Фикстуры статусов захвата (issue #6)

`example/repository/2.21-locks/` — файл `1cv8ddb.1CD` двух платформ (`8.5.1`, `8.3.27`), вывод `/Out`
отказа захвата (`lock-refused.out.txt`) и (для 8.5.1) снятые байты обменов с crserver (`tcp/`, `http/`,
`designer-devObjectsStatistic.request.bin`) — собирает `example/tools/build-repository-locks.mjs` (по
образцу `build-supported-cf.mjs`, см. выше); полное описание шагов, использования и формата — в шапке
скрипта. `example/repository/tls/localhost.{crt,key}` (самоподписанный сертификат для теста https-
транспорта) регенерируется отдельно, флагом `--tls`. Ожидаемые захваты и отказы сверяются с
`example/2.21/src/cf/ConfigDumpInfo.xml` по uuid — при пересборке `example/2.21` с новыми uuid эту
фикстуру нужно пересобрать тоже (обычным запуском без `--tls`), иначе тесты статусов захвата ссылаются на
несуществующие объекты.

### Фикстуры частичного отказа рекурсивного захвата (issue #87)

`example/repository/2.21-partial-locks/` (два объекта: Petrov держит подчинённую форму одного справочника
и корень другого, Admin захватывает оба рекурсивно) и `example/repository/2.21-partial-root/` (Petrov
держит один справочник, Admin захватывает корень конфигурации рекурсивно) — тот же
`build-repository-locks.mjs`, свой `scenario.json` в каждом каталоге и запуск с `--out <каталог>` без
`--network` (сетевой обмен для этого сценария не снимался). Раскладка результата та же, что у
`2.21-locks`, но `run.json` без сетевых секций, а вместо `lock-refused.out.txt` — по одному `/Out`-файлу
на шаг сценария (`log` шага), т.к. фикстуры воспроизводят несколько разных случаев частичного отказа
(отказана подчинённая единица члена, отказан якорь-член при захваченных подчинённых, повторный частичный
захват без новых успехов). Формат шага сценария и поле `expect` (ожидаемые `grants`/`refusals` `/Out`
шага) — в шапке скрипта; `locks.allUnitsExcept` в итоговой проверке захватов означает «все единицы
`ConfigDumpInfo.xml`, кроме перечисленных», без чего сценарий рекурсивного захвата почти всей
конфигурации (`2.21-partial-root`) пришлось бы перечислять построчно. Как и `2.21-locks`, обе фикстуры
привязаны к uuid `example/2.21/src/cf/ConfigDumpInfo.xml` и пересобираются вместе с ним.

## Ручная проверка на Конфигураторе

Проверено в пакетном режиме (§10.12 плана): имена `-listFile`, состав частичной выгрузки, `-configDumpInfoOnly`,
`-revised`, `unlock` с `-force` и без, рекурсивный и нерекурсивный захват объекта и подсистемы, нерекурсивная
отмена после рекурсивного захвата, новая форма при нерекурсивном получении/захвате. Readonly скрытой
вкладки, обеих сторон диффа и временной вкладки (issue #63) — покрыто автоматизированными тестами в реальном
Extension Host (`sessionReadonly.test.ts`, `readonlyTabSelection.test.ts`, `openMergeDiffs.test.ts`,
`editorReadonlyController.test.ts`). Остаётся проверить в интерактивном
VS Code: `files.readonlyInclude`, диалог конфликта с реальным сценарием двух пользователей, режим агента
конфигуратора, расширение (cfe) с формами.
